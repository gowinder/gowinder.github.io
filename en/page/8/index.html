The Trouble Caused by the Server's Automatic Time Sync Service

Author published on 2010-03-12

Soldiers Sortie had an outage once, and the cause was the sync service pulling the time backwards. That meant the current time could end up earlier than the timestamp of an event already recorded in memory, so subtracting one from the other produced a negative number — and since we were using DWORD, it became an enormous value and corrupted the data.
The fix: first, it’s best to turn off the time sync service on the server; then check the DWORD difference and skip the operation if it’s negative. I think DWORD has to be used with care — I’ve run into trouble on this more than once!

When the Elements of a Priority Queue Are Pointers

Author published on 2010-03-12

Using a priority queue whose elements are pointers, like this:
typedef priority_queue<TimeEvent*, deque <TimeEvent*>, less<deque<TimeEvent*>::value_type> TIME_EVENT_QUEUE;
Compared this way, the result is a comparison of pointer values. If I want to compare some member of TimeEvent, that doesn’t work. After some Googling, there’s an approach: replace less with a functor struct:
struct TimeEventLessComp
{
bool operator () (TimeEvent*& a, TimeEvent*& b) const
{
return a->dwTick > b->dwTick;
};
};
Then change the declaration to:
typedef priority_queue<TimeEvent*, deque <TimeEvent*>, TimeEventLessComp> TIME_EVENT_QUEUE;

How to Implement a Time Service

Author published on 2010-03-11

Use a singly or doubly linked list, or a priority queue (priority_queue). Each element in the queue is a timer object. A timer object holds the time difference measured from a standard point in time (when the program started running) — the later a timer is supposed to fire, the larger this value — along with the trigger event type. If you only use a linked list, you have to re-sort after every insertion. With a priority queue the insertion position is handled automatically, so I figure the priority queue should work better, though I still need to test it. On every heartbeat (the server thread loop), the time service’s OnTicker function is called. It checks the time value of the first timer in the queue, and if the current time difference has reached or passed it, the timer is popped out and its trigger event is called. Stress Testing Notes 1

Author published on 2009-07-14

Closed beta is almost here, so we’ve started stress testing.
1000 connections was fine, but the problems showed up after login: handling a single login takes one second, so you can imagine how long 1000 of them would take.
That obviously won’t do.
So I added some test statements to find out who was dragging things out.
In the end it turned out to be the player task initialisation at login — there are over 900 tasks, each with sub-tasks, and every sub-task does a SELECT against the database whether or not there’s a record. No wonder. Tomorrow I’ll get someone to fix it: completed tasks and tasks that haven’t started yet don’t need to be read at all. That should speed things up a lot.
Then I found another problem with log writing. In the function called on every TICK, if a CHECK-style log fires an error, it keeps writing and the server stops responding. Apart from turning off logging to disk, there’s almost nothing else you can do. When the UI thread displays things, each time it pulls a log message it now checks whether that would exceed the time available for this TICK; if it would, the unprocessed TICKs get handled next time, so the UI doesn’t freeze.
